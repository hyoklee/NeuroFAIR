- [clio-fs and the CLIO HDF5 VFD](concept-clio-fs-vs-hdf5-vfd.md) — how the two relate: **clio-fs is the layer the VFD sits on**. clio-fs = the `filesystem` ChiMod over the CTE (pool `clio_cte_filesystem` 560.0, paths→CTE tags, offsets→1 MiB page blobs, `CLIO_CFS_CLIENT` descriptor API); the HDF5 VFD (`clio_vfd`, value 3200) is one of five front ends that delegate to it (verified `CLIO_CFS_CLIENT` call counts: libfuse 36, posix 33, stdio 25, mpiio 8, **vfd 8**, **hdf5_vol 0**). The VFD calls only `OpenFd/PwriteFd/FtruncateFd/CloseFd/RemovePath` — **no `PreadFd` anywhere**, which *is* the populate-only tier and the reason it tracks native on reads. Also: the `clio::` marker is a clio-fs concept the POSIX adapter routes on but the VFD **refuses** (explaining both the "tier stayed at 0 bytes" symptom and why VFD/VOL need no app change); and the VOL bypasses clio-fs entirely for CTE-core blobs, which is why only it can serve reads from the tier. clio-core `dev` `3357ac99`

## Performance Studies
- [MiV case 6 on **Frontera** — clio-core HDF5 **VOL** adapter vs native HDF5](miv_frontera_case6_vol.md) — first end-to-end **VOL** read of case 6 on any machine (via `HDF5_VOL_CONNECTOR=clio`, no LD_PRELOAD). Unblocked by a **neuroh5 fix**: 3 attribute-enum callbacks in `cell_attributes.cc` used deprecated **`H5Gget_objinfo`** (native-VOL-only) → empty `cell_attribute_info` through any non-native VOL → `make_cells` KeyError; replaced with VOL-neutral **`H5Lexists`** (the clio connector itself matches the reference H5VLpassthru — not at fault). Result (1 node, NR=1): VOL reads the whole network at **native within ~0.15%** (connected-cells 335.1 vs 334.6 s) — **compute-bound + read-once ⇒ no CTE speedup**, same as Vista/ares/jelly/Polaris. Open VOL limits: **multi-rank MPI-collective reads deadlock**; **results-file write-open (`h5py "a"` of a new file) fails**. Built in `miv-stack.sif` (gcc-13, phdf5 1.14.6). `claude.md`'s PBS/`gpu_hack_large` → Frontera `development`.
- [MiV case 6 on **Vista** (ARM/Grace) — IOWarp CTE vs native HDF5](miv_vista_case6.md) — full from-scratch **aarch64** bring-up (NEURON 9.0.1, neuroh5 0.1.18, miv_simulator 0.3.0, parallel h5py on phdf5/1.14.6; clio-core `dev` CTE with **ELF=ON** → `libclio_cte_posix.so`, no source patches). Case 6 (187 cells, 160,528 synaptic + **107 gap-junction** edges) **runs end-to-end**; native HDF5 **scales cleanly 1→2→4 nodes** (connected-cells 45.2→27.4→16.1 s, 2.80×). **CTE = native within noise** (1 node): compute-bound + the POSIX adapter's `clio::`-only routing means neuroh5's MPI-IO reads bypass the tier. 4 MiV `vista-arm-fix` patches **Also: 2-node distributed CTE cluster formed over InfiniBand (ib0), neighborhood=2 — runs case 6 with no deadlock; CTE=native within noise at 2 nodes too.**
- [MiV case 6 on **Vista** (ARM/Grace) — clio-core HDF5 **VOL** connector vs native vs POSIX](miv_vista_case6_vol.md) — case 6 run through the clio **HDF5 VOL connector** (`HDF5_VOL_CONNECTOR=clio`, `libclio_hdf5_vol.so` built against the same `phdf5/1.14.6` h5py links). **Runs end-to-end incl. writing results; output bit-identical to native (`h5diff`=0).** Three-way (same dev build, 1 node/4 ranks): native 70.10 s ≈ POSIX 71.21 s ≈ VOL 70.88 s — all within ~1–2 % noise (compute-bound + read-once ⇒ no CTE win), but unlike the `clio::`-only POSIX interceptor the **VOL actually sees neuroh5's reads**. **Goes past [Frontera](miv_frontera_case6_vol.md)**, which left the results-file write-open and multi-rank collective reads unresolved: both work on Vista (4- and 8-rank complete). Two MiV-stack fixes, **neither a connector bug** (HDF5 blocks them above the connector): (1) neuroh5 rebuilt off deprecated v1 iteration APIs (`H5Literate1`/`H5Gget_objinfo` → `H5Literate2`/`H5Lexists`, branch `fix/vol-h5literate2`); (2) `bin/sitecustomize.py` shim makes h5py `File(...,"a")` VOL-robust (HDF5's H5VL layer masks the `errno=2` so h5py's create-fallback is skipped) — no-op unless `HDF5_VOL_CONNECTOR` set. clio-core `dev` `b5c68c5e` stays pristine.

- [MiV case 6 (gap junctions) — native parallel HDF5 on jelly](miv_jelly_case6.md) — full from-scratch bring-up on the HDF Group **jelly** node (gcc 10.2.0 + OpenMPI 5.0.5 + parallel HDF5 1.14.6, NEURON 9.0a0, neuroh5 0.1.18, miv_simulator 0.3.0). Case 6 (187 cells, ~3.27M synaptic edges, 102 PYR↔PYR gap junctions) **builds and runs end-to-end**; **near-ideal single-node rank scaling** (tstop=50): total wall 105.9 s (4) → 58.8 s (8) → 33.1 s (16), connected-cells phase 82.6→43.3→23.4 s (88–95% par. eff.). Native-HDF5 baseline (no IOWarp); 8 bring-up blockers fixed; STIM input spikes omitted (fork `generate-input-features` API bug)
- [IOWarp/clio-core CTE on jelly — built from source + a measured I/O win](miv_jelly_iowarp.md) — **IOWarp CTE built on CentOS 7** (conda gcc-13 + 2 portability patches: libaio, `memfd_create`→syscall; io_uring off for kernel 3.10). On jelly's slow HDD-RAID `/mnt/wrk` (~250–300 MB/s device), the **CTE RAM tier is ~7–10× faster** for I/O-bound write/uncached-read (1.9–2.4 GB/s) — a clear "IOWarp can help" in its regime — while warm page cache (2.9 GB/s) wins for small read-once data (why the compute-bound MiV sim doesn't benefit). Globus CLI installed but jelly isn't an endpoint, so large NeuroH5 generated locally
- [Distributed CTE memory pool: nene (macOS) + jelly (Linux)](miv_jelly_distributed_pool.md) — **2-node, 2-OS CTE cluster** over ZeroMQ/TCP on one LAN; bidirectional inter-node RPC forms despite macOS↔Linux + 2-commit skew. Real case-6 HDF5 inputs stored on the **remote (nene) RAM tier** and read back **byte-identical** (integrity PASS). Cross-node tier is **link-bound at ~11 MB/s** — nene is on 100baseTX Fast Ethernet (raw TCP 11.3 MB/s), ~35× slower than jelly's RAID. Refines the >125 GB finding: a distributed pool *adds* the capacity a single-node RAM tier can't, but only helps >RAM reads on a fast fabric (≥10–40 GbE)
- [4-node distributed CTE pool: nene + jelly + raven + macmini-m1](miv_4node_distributed_pool.md) — extends the above to a **4-node, 3-OS, 2-ISA** cluster (macOS/x86-64 + CentOS7/x86-64 + Windows10/x86-64 + macOS/**arm64**), all at `dev b1e087c3`. Every pool forms with 4 containers; real case-6 inputs (`MiV_Connections` 8.90 MB, `MiV_Cells` 36.48 MB) stored on **each node individually + distributed** and read back **byte-identical** (integrity PASS on all) — first time the Windows and Apple-Silicon nodes hold real case-6 data. A 5 GB synthetic fill spreads across all 4 tiers (RSS-verified). Throughput is **LAN-bound (~4–10 MB/s) for every routing mode incl. `local`**: at `neighborhood: 4` the `max_bw` DPE distributes placement cluster-wide, so bytes always leave the client node. Reconfirms at 2× scale: **interconnect bandwidth, not capacity, is the ceiling**. Also exercises both HDF5 adapters: case-6 datasets read through the **`clio` HDF5 VOL connector** are **byte-identical** to native (`h5dump`, HDF5 1.14.6, loads via `HDF5_VOL_CONNECTOR=clio`, no app change) — but `CLIO_VOL_TRACE` proves those reads are **native passthrough** (tier unused). The **POSIX interceptor** (`libclio_cte_posix.so`, built with `ELF=ON` + 3 CentOS-7 shims) is write-through: an 8.9 MB case-6 file round-trips **byte-identical through the 4-node tier** (`clio_cte_filesystem` chimod, pool 560.0). Complementary: POSIX stages bytes into the pool, VOL reads existing HDF5 transparently. **Read-perf** (same case-6 payload): tier reads are LAN-bound — POSIX **14 MB/s** > raw blob **5.7–8.5 MB/s**; the unpatched VOL (~39 MB/s) read the **native file, tier bypassed** (`served:native`). A compound/whole-read **VOL patch** ([clio-core#751](https://github.com/iowarp/clio-core/pull/751)) then makes reads genuinely **serve from the CTE tier** (`served:cache`, ~20 MB/s — fastest tier path), but that's ~6× slower than native page-cache here: a functional enablement, not a speedup on this LAN-bound cluster
